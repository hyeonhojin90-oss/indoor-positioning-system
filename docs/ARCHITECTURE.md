# System Architecture

## 1. 아키텍처 목표

셔틀버스 위치 확인, 하차 후 실외 보행과 건물 내부 강의실 안내를 하나의 사용자 흐름으로 연결한다. 각 구간은 서로 다른 위치 정보와 센서를 사용하므로 측위 주체, 좌표 출처와 전환 조건을 명확히 분리한다.

## 2. 전체 서비스 흐름

```text
[버스 내부 T-Beam GPS]
        ↓
셔틀 위치 수신·저장·오차 분석·보정
        ↓
사용자에게 셔틀 위치 및 하차 정보 제공
        ↓
[정류장 하차]
        ↓
[사용자 휴대폰 GPS]
        ↓
정류장 → 목적 단과대학 입구 보행 안내
        ↓
건물 접근·진입 판단
        ↓
[실외 측위 → 실내 측위 전환]
        ↓
PDR + 자기장 기반 보정 + 지도 정합
        ↓
층·복도·강의실 위치 및 경로 안내
        ↓
[Android UI / 2D 지도 / 향후 AR]
```

T-Beam 좌표는 버스의 위치이고 휴대폰 GPS 좌표는 하차한 사용자의 위치다. 두 좌표를 같은 측위 주체의 연속 데이터로 취급하지 않는다.

## 3. 주요 모듈

### 3.1 Shuttle GPS Module

위치: `gps/`

역할:

- 버스에 장착할 T-Beam의 GPS 위치 수신
- 원시 NMEA·위치·품질 데이터 기록
- 정지 및 운행 상태의 GPS 정확도 분석
- 실제 데이터 특성에 맞는 보정 방식 선정
- 원본과 보정 결과를 분리해 제공

현재 상태:

- Arduino UNO와 NEO-7M 기반 원시 NMEA 수신 스케치가 보존되어 있다.
- T-Beam 실제 모델·펌웨어 환경 확인과 정식 데이터 수집은 아직 진행 전이다.
- 보정 알고리즘은 실제 원시 데이터 분석 전까지 확정하지 않는다.

### 3.2 Outdoor Pedestrian Guidance Module

주 실행 위치: 향후 `app/`

역할:

- 하차 후 사용자 휴대폰 GPS 위치 수신
- 정류장과 목적 단과대학 입구 사이 보행 경로 안내
- GPS 정확도와 위치 갱신 상태 확인
- 건물 접근 또는 진입 이벤트 생성
- 실내 위치 추정 모듈로 전환

버스용 GPS 데이터와 사용자 휴대폰 GPS 데이터는 출처와 목적이 다르므로 데이터 모델에서도 구분한다.

### 3.3 Indoor Positioning Module

현재 실험 위치: `indoor/web/`

향후 실행 위치: `app/`

역할:

- 가속도계 기반 보행 감지
- 걸음 수와 보폭을 이용한 이동거리 추정
- 자이로스코프·자기장 센서를 이용한 방향 추정
- PDR 위치 계산과 누적 오차 추적
- 자기장 특징과 지도 구조를 이용한 위치 보정
- 기압계 기반 층 변화 보조 판단
- 계단·엘리베이터 이동과 층간 전환 판정

기본 흐름:

```text
휴대폰 센서 원시값
→ 보행·방향·거리 추정
→ PDR 상대 위치
→ 자기장 특징 비교
→ 복도·벽·경로 그래프 지도 정합
→ 보정된 실내 지도 좌표
```

Wi-Fi RTT는 보조 측위 후보다. 실제 건물 공유기와 휴대폰의 지원 여부, 측정 가능 거리와 정확도를 시험한 뒤에만 모듈 통합 여부를 결정한다.

### 3.4 Map and Routing Module

위치: `indoor/web/`

역할:

- 1~10층 건물 구조와 강의실 데이터 관리
- 코어·계단·엘리베이터·복도 좌표 관리
- 실내 위치를 지도 좌표에 정합
- 목적지 검색과 향후 경로 그래프 제공
- 2D·3D 지도 표현

현재 파일 구성:

- `data/maps/floor-01.json`~`floor-10.json`: 층별 지도 데이터
- `data/maps/floor-04.json`: 공통 본동·코어 기준 데이터
- `src/map-2d.js`: 메인 2D 지도
- `src/map-3d.js`: 1~10층 단독·통합 3D 지도
- `src/pdr.js`: 3·4층 PDR·자기장 실험 화면
- `pages/floors/`: 층별 2D 구조 검토도
- `data/sensors/magnetic/`: 자기장 측정 자료

3D는 확정된 2D 구조를 기준으로 만들며 지도 구조 규칙은 `indoor/AGENTS.md`를 따른다.

### 3.5 Application Module

위치: `app/`

역할:

- 목적 강의실 검색과 사용자 입력
- 셔틀 위치, 사용자 위치와 측위 상태 표시
- 실외·실내 안내 모드 전환
- 경로, 다음 행동과 남은 거리 표시
- 센서 권한과 측위 실패 상태 처리
- Android 카메라 기반 AR 안내
- AR 미지원 또는 추적 손실 시 2D 지도 대체 안내

현재는 앱 구현 전이다. Windows 환경에서 Android를 먼저 개발하고 실제 기기에서 핵심 흐름을 검증한 뒤 iOS 지원 범위를 검토한다.

## 4. 위치 데이터 구분

최소한 다음 위치 유형을 구분해야 한다.

| 위치 유형 | 측위 주체 | 주요 출처 | 사용 구간 |
| --- | --- | --- | --- |
| 셔틀 위치 | 버스 | T-Beam GPS | 셔틀 접근·운행 확인 |
| 사용자 실외 위치 | 사용자 휴대폰 | 휴대폰 GPS | 정류장→건물 입구 |
| 사용자 실내 상대 위치 | 사용자 휴대폰 | PDR | 건물 내부 이동 |
| 사용자 실내 보정 위치 | 사용자 휴대폰 | PDR·자기장·지도 정합 | 강의실 경로 안내 |
| 층 위치 | 사용자 휴대폰 | 기압계·계단/엘리베이터 이벤트 | 층간 이동 |

모든 위치 데이터에는 가능한 경우 `timestamp`, 좌표계, 출처, 정확도 또는 신뢰도와 측위 상태를 함께 전달한다.

## 5. 실외·실내 전환

전환 조건은 아직 실험으로 확정하지 않았다. 후보는 다음과 같다.

- 목적 건물 입구 반경 진입
- 휴대폰 GPS 정확도 저하 또는 위성 신호 변화
- 사용자의 명시적 실내 모드 시작
- 지도상 입구 기준점 통과
- Wi-Fi·자기장 등 건물 내부 특징 확인

한 가지 신호만으로 자동 전환을 확정하지 않고 실제 현장 시험을 통해 오작동과 전환 지연을 비교한다. 자동 판정이 불확실하면 사용자 확인을 제공한다.

## 6. 저장소 영역

- `docs/`: 전체 구조, 설계 결정, 상태와 작업 기록
- `gps/`: 셔틀 GPS 펌웨어, 원시·가공 데이터, 분석 코드와 실험 문서
- `indoor/web/`: 정적 웹 기반 1~10층 2D·3D 지도와 PDR 실험
- `indoor/tools/glb-viewer/`: LiDAR·GLB 검사와 변환 도구
- `app/`: Android 우선 사용자 애플리케이션

## 7. 현재 구현과 목표 구조의 차이

- 지도와 PDR 실험 화면은 `indoor/web`에 구현되어 있다.
- 실제 휴대폰 센서 수집, 실외·실내 자동 전환과 경로 안내 앱은 아직 구현 전이다.
- GPS 폴더에는 UNO 기반 원시 수신 스케치만 있으며 T-Beam 운행 데이터는 아직 없다.
- 지도 데이터는 1~10층까지 존재하지만 전체 층 경로 그래프는 아직 완성되지 않았다.
- Android 앱 구현 시 웹의 지도 데이터를 복제하지 않고 공용 인터페이스로 분리해야 한다.

중요한 구조 변경은 `docs/DECISIONS.md`, 현재 구현 상태 변경은 `docs/CURRENT_STATUS.md`에 기록한다.
