# 실내 측위 전체 구조와 Wi-Fi RTT 확인 계획

마지막 갱신: 2026-09-07

현재 구현 계약은 [FUSION_V1.md](FUSION_V1.md)를 따른다. 구역 판별/2D 파티클/영역 제약/시간 기반 수직 상태를 Expo 비교 엔진에 처음 연결했다. 아래 초기 상태·RTT 계획은 과거 설계 근거이며 오늘의 미완료 작업 목록이 아니다. 전체 현재 상태는 `docs/CURRENT_STATUS.md`가 기준이다.

## 1. 현재 결론

실내 측위의 기본 경로는 다음과 같이 유지한다.

```text
센서 원시값
→ PDR 상대 이동 추정
→ 자기장 특징 기반 보정 후보 생성
→ 지도 정합·경로 그래프 제약
→ 신뢰도 평가
→ Android 지도 안내
```

Wi-Fi RTT는 기본 전제가 아니라 선택적 보조 관측값이다. 지원되지 않거나 측정 품질이 낮으면 PDR·자기장·지도 정합만으로 계속 동작해야 한다.

## 2. 초기 구현과 한계 (2026-08-29 당시 기록)

- `indoor/web/src/pdr.js`는 3·4층 실험용으로 수동 걸음 입력, 브라우저 `DeviceMotion`/`DeviceOrientation`, 복도 선분 스냅과 4층 자기장 `Btotal` 최근접 보정을 구현한다.
- `indoor/web/data/maps/floor-04.json`에는 4층 복도·시설·방 좌표와 15개 자기장 지문이 있고, 다른 층은 자기장 지문이 실험용으로 채워지지 않았다.
- `indoor/web/data/sensors/magnetic/floor-04.json`은 두 번의 왕복 CSV 요약과 수동 기준점을 보존하지만, 방향·자세·시간 동기화가 포함된 공통 지문 데이터셋은 아니다.
- 현재 그래프는 실험 화면에서 3·4층만 구성된다. 전체 층 경로 그래프와 실제 Android 센서 수집 모듈은 아직 없다.

## 3. 런타임 모듈

### 3.0 Automatic initialization

최종 사용자 앱은 정상 흐름에서 층·시작 지점·최초 방향 입력을 요구하지 않는다. 초기화는 다음 두 시나리오로 분리한다.

1. `외부→내부 연속 안내`: 마지막 실외 GPS, 건물 접근 방향, 기압·방위와 지도 진입 노드를 이용한다. 진입 후보는 최소 `1층 정문`, `1층 좌·우 사이드계단`, `5층 야외 연결부`이며 첫 구현은 1층 정문만 지원한다. GPS 정확도가 출입문 구분에 부족하면 정문 기준점에서 `실내 안내 시작` 버튼을 누르게 하는 반자동 방식을 사용한다.
2. `건물 내부에서 앱 실행`: 가능한 `(floor, edge, progress, direction)` 후보를 동시에 생성하고 정지 센서 관측으로 순위를 계산한다. 앱은 `여기로 예상됩니다` 카드에 층·강의실/시설 후보를 표시하고, 사용자가 `맞아요 · 안내 시작`으로 확인하면 해당 노드를 PDR 기준점으로 확정한다. 틀리면 `아니에요 · 현재 위치 선택`에서 층과 지도상의 강의실·시설을 검색한다.

외부/내부 분류는 `UNKNOWN`, `OUTSIDE`, `ENTRY_CANDIDATE`, `INSIDE` 상태로 관리한다. 최근 여러 GPS 위치와 정확도 원이 건물 외곽 폴리곤 및 각 진입 구역과 겹치는 정도, 접근 궤적의 방향과 연속성을 사용한다. 1층과 5층의 약 4개 층 차이는 같은 시간대라면 약 `1.76 hPa`이므로 진입점 선택의 보조 근거가 될 수 있지만, 날씨 변화가 포함된 과거 절대기압과의 단순 비교는 금지한다.

사용자에게는 내부 상태 머신을 그대로 노출하지 않고 `현재 건물 외부에 계신 것으로 확인됩니다` 또는 `현재 건물 내부에 계신 것으로 확인됩니다` 카드만 표시한다. `맞아요 · 안내 시작`을 누르면 외부는 진입구까지 GPS 안내, 내부는 현재 층·강의실 후보 확인으로 진행한다. `아니에요`를 누르면 외부·내부 두 선택지만 제공해 환경 상태를 즉시 수정한다.

내부 정지 콜드스타트는 3~5초 센서 창에서 자기장 크기·분산·방위·기압을 추출하고 기존 라벨 시점 주변 노드 지문과 비교해 상위 후보를 만든다. 앱은 우선 예상 위치를 사용자에게 확인받고, 틀리면 지도 기반 현재 위치 선택을 제공한다. 5~10 m 이동 요청은 사용자가 실제 위치도 선택할 수 없을 때의 추가 탐색 기능으로만 사용한다.

초기 절대 방위는 지도 복도 축과 비교해 후보를 줄인다. 현장 관측상 왼쪽 복도 약 `175°`, 코어에서 메인복도 약 `270°`, 오른쪽 복도 약 `350°`가 1차 기준이지만 자기장 교란과 기기 자세 때문에 고정 범위만으로 위치를 확정하지 않는다. 걸음 수와 회전 순서, 통과 가능한 지도 연결, 상대기압 변화, 짧은 자기장 패턴을 순차 반영해 후보 확률을 갱신한다. 최고 후보와 차순위의 격차가 충분할 때만 안내 위치를 확정하며 그 전에는 `위치 확인 중` 상태를 유지한다.

현재 통제 실험의 수동 시작 층·지점·방향 선택은 각 관측기의 오차를 따로 검증하기 위한 기능이다. 최종 안내에서는 앱 추정 후보 확인 또는 지도 기반 현재 위치 선택으로 대체하고 방향은 센서에서 자동으로 얻는다. 추가 이동 요청은 사용자가 현재 위치도 알지 못할 때만 선택적으로 제공한다.

환경 판정 확인과 수정은 `environment_confirmed`, `environment_corrected`로 저장한다. 위치 확인과 수정은 각각 `user_confirmed`, `user_corrected` 이벤트로 저장한다. 이벤트에는 앱의 원래 후보·점수, 사용자가 선택한 실제 상태 또는 노드와 확인 시각을 함께 기록해 자동 추정 정확도 평가에 사용하되, 검토 없이 학습 정답으로 병합하지 않는다.

### 3.1 Sensor collector

Android에서 가속도계, 회전 벡터/자이로스코프, 자기장 센서, 기압계를 timestamp와 센서 정확도와 함께 수집한다. 센서 권한 거부·센서 미지원·값 고정은 측위 상태에 반영하고 PDR을 중지하거나 신뢰도를 낮춘다.

### 3.2 PDR estimator

가속도 신호에서 보행 주기를 검출하고, 초기 실험으로 보정된 사용자별 보폭을 적용한다. 회전 벡터와 자이로스코프를 결합해 지도 좌표계의 진행 방향을 계산하며, 휴대폰 방향 보정 기준점을 건물 입구 또는 엘리베이터 앞에서 설정한다. PDR 출력은 `floor`, `x`, `y`, `heading`, `stepCount`, `positionCovariance`, `timestamp`를 가진다.

### 3.3 Magnetic matcher

단일 `Btotal` 값만으로 위치를 확정하지 않는다. 가능한 경우 축별 자기장, 크기, 변화율과 이동 방향을 짧은 구간으로 묶어 지도상의 지문 구간과 비교한다. 후보가 여러 개이거나 환경 변화가 크면 보정량을 제한하고 신뢰도만 낮춘다. 4층 자료는 초기 검증용이며, 층별 왕복 측정으로 확장한다.

### 3.4 Map matcher

현재 위치를 복도 중심선·교차점·계단/엘리베이터 접근 노드에 투영한다. 벽 통과, 방 내부 진입, 존재하지 않는 연결을 금지하고, 지도 오차가 확인되지 않은 구역은 `estimated` 또는 `uncertain` 상태로 표시한다. 지도 좌표는 2D JSON을 단일 기준으로 사용한다.

### 3.5 Floor and vertical transition

기압 변화, 계단 걸음 패턴, 엘리베이터 정지/이동 상태와 지도상의 수직 링크를 함께 사용한다. 하나의 신호만으로 층을 확정하지 않고, 수직 이동 후보를 먼저 만들고 도착 후 층 기준점에서 재초기화한다.

### 3.6 Optional RTT observer

RTT가 사용 가능할 때만 주변 RTT AP의 거리·표준편차·측정 성공 여부를 수집한다. AP 좌표가 3개 이상이고 품질이 충분할 때 multilateration 후보를 만들며, 결과는 PDR를 대체하지 않고 보정 관측값으로 전달한다. AP 수 부족·실패율 증가·잔차 증가 시 자동으로 무시한다.

### 3.7 Fusion and confidence

초기 구현은 칼만 필터를 미리 확정하지 않고, 각 관측의 잔차·분산·시간 경과를 이용한 가중 보정으로 시작한다. 이후 실제 로그로 성능을 비교해 EKF/UKF 또는 입자 필터 도입 여부를 결정한다.

```text
PDR prediction
  + magnetic candidate likelihood
  + map projection constraint
  + optional RTT range likelihood
  + vertical transition evidence
→ fused pose + confidence + reason codes
```

### 3.8 Cross-device reference data

Galaxy와 iPhone 로그는 모두 추정 근거로 사용하되 원시 행을 직접 합치지 않는다. Android 약 500 Hz와 iPhone 약 20 Hz 가속도는 공통 시간축과 공통 보행 특징으로 변환하고, 방위는 원형 각도로 처리한다. 자기장은 기기별 3축 절대값 대신 세션 정규화 `Btotal`, 변화율과 짧은 구간 패턴을 우선하며 상대기압은 시작 기준 변화량으로 사용한다.

Galaxy 로그는 현재 여러 층·좌우·특수 경로의 지도 앵커와 방향·보행 기준을 제공한다. iPhone 로그는 현재 4층 오른쪽 복도 3회만 있으므로 그 구간의 iOS 반복성과 플랫폼 보정에만 직접 사용하고, 다른 층의 iPhone 자기장 지문으로 간주하지 않는다. 런타임에서는 플랫폼별 관측 분산을 따로 두고 공통 지도 좌표에서 후보 점수만 결합한다.

## 4. Wi-Fi RTT 지원 확인 (초기 실험 계획 기록)

지원 단말에서 AP12개/responder0개를 관측한 1차 확인은 완료했다. 현 단계 RTT 거리측정은 제외하며 아래 계획은 새 지원 AP 근거가 생길 경우의 재검토용이다.

### 단말 확인

Android 진단 화면 또는 테스트 앱에서 다음을 기록한다.

1. 제조사·모델명·Android/API 버전
2. `PackageManager.hasSystemFeature(PackageManager.FEATURE_WIFI_RTT)` 결과
3. `WifiRttManager.isAvailable()` 결과
4. `WifiRttManager.getRttCharacteristics()`의 802.11mc/802.11az 관련 capability
5. Wi-Fi 켜짐, 위치 서비스 켜짐, 필요한 권한 승인 여부

Android 공식 문서상 RTT API는 Android 9(API 28)에서 도입되었고, Android 13(API 33) 이상을 대상으로 하는 앱은 `NEARBY_WIFI_DEVICES` 권한이 필요하다. 실제 앱에서는 위치 산출 목적에 필요한 `ACCESS_FINE_LOCATION`과 런타임 상태도 함께 점검한다.

### 건물 AP 확인

각 층의 AP 관리 화면 또는 설치 업체 자료에서 다음을 확인하고 AP MAC/BSSID, 모델, 층·좌표를 목록화한다.

- IEEE 802.11mc FTM 또는 802.11az 지원 여부
- RTT responder 활성화 여부와 펌웨어/설정
- 각 층에서 동시에 보이는 RTT AP 개수
- AP의 실제 지도 좌표와 설치 높이

AP가 일반 Wi-Fi 접속이 된다는 사실만으로 RTT responder임을 의미하지 않는다.

### 현장 판정 실험

각 층의 코어, 중앙 복도, 양쪽 끝, 계단/엘리베이터 앞에 기준점을 만든다. 각 점에서 정지 상태 RTT를 반복 측정하고, 3개 이상 AP가 동시에 성공하는지, 거리 잔차와 실패율, 방향·사람 밀집·문 개폐에 따른 변화를 기록한다. 동일 경로를 PDR 단독, PDR+자기장, PDR+RTT, 세 조합으로 왕복해 위치 오차와 층 전환 오작동을 비교한다.

채택 기준은 실험 전에 정한다. 예시는 `동시 유효 AP 3개 이상`, `측정 성공률 80% 이상`, `기준점 평균 오차와 95백분위 오차가 PDR 단독보다 개선`, `배경 동작에서 과도한 배터리 사용 없음`이다. 수치는 실제 요구 정확도와 측정 결과에 따라 확정한다.
