## 보정이 실제로 작동했는가

- 자기장 8걸음 V2는 도착 시점까지 총 36개 창을 평가했지만 **적용 0회**다. 대부분 `ambiguous_sequence`, 일부는 `outside_pdr_gate`다.
- BLE는 총 65개 창을 평가했지만 **적용 0회**다. 60개가 `no_usable_features`, 5개가 `insufficient_ble_window`다.
- 따라서 이번 네 회의 모드 4 결과는 실질적으로 **PDR + 지도 파티클 제약** 결과다. 자기장·BLE가 오차를 복구했다고 해석하면 안 된다.
- 별도 현재 코드 재생도 PDR 약 2.268m와 모드4 약 2.268m로 차이가 거의 없었다. Android 방향값의 정수 반올림과 동일값 750ms 전송 간격을 재생에 반영해도 현장 저장 평균 3.16m와 일치하지 않았다. 기존 로그에는 엔진에 실제 전달된 `heading_degrees` 이벤트가 없고 센서 콜백·WebView 전달 순서를 완전히 복원할 수 없어 차이의 원인을 단정할 수 없다. 성능 판정에는 현장 저장값 3.16m를 우선한다. 새 앱은 앞으로 실제 전달한 방향 이벤트를 별도로 저장한다.

## BLE가 0회 적용된 원인

각 회차에서 BLE 주소 기반 익명 ID는 169~189개였지만 기존 운영 기준지문 전체와 공통인 ID는 9~11개뿐이었다. 분리된 5초 창에서는 사용할 수 있는 공통 특징이 더 줄어 보정이 거부됐다. 주소 회전은 가능한 원인 중 하나지만, 날짜·동선·스캔 조건·기준지문 구성의 영향도 분리되지 않아 원인을 확정하지 않는다.

반면 같은 날 바로 왕복한 두 경로끼리는 오른쪽 113개, 왼쪽 136개의 주소 ID가 공통이고 RSSI 중앙 절대차는 2.5dB·3.5dB였다. 새로 기록한 광고 payload 해시도 왕복 간 제조사 65·92개, 서비스 20·10개가 공통이었다. 같은 날 반복성은 있으나 날짜가 다른 기준지문과의 안정성은 아직 증명되지 않았다. 기존 주소 ID 기준 BLE 지문을 그대로 운영 보정에 쓰기는 어렵다.

## 걸음과 진행량

- **왼쪽 복도 비교 정정**: 정방향은 도착 랩 직전 모드4가 73걸음·4.87m 부족했지만, 랩 후 0.64~1.14초 사이에 3걸음이 더 반영돼 최종 76걸음·3.01m 부족으로 끝났다. 역방향은 도착 랩과 최종 모두 76걸음·1.51m 부족했다. 따라서 `73 대 76걸음`을 전체 보행의 실제 걸음 검출 차이로 단정하면 안 된다. 랩 후 3걸음이 계속 걸은 결과인지 처리 지연인지는 현재 로그만으로 분리되지 않으므로 현장 성능 판정은 도착 랩 직전 4.87m를 유지한다.
- 왼쪽 정방향과 역방향의 검출 걸음당 중앙 이동량은 둘 다 약 0.619m였다. 정방향 초반 1걸음은 코어에서 진행량이 거의 없었고, 8번째 걸음은 `heading_unavailable`로 진행하지 않았다. 역방향에는 이런 0m급 걸음이 없었다. 이 두 구간은 도착 후까지 남는 약 3m 부족의 일부를 설명한다. 나머지는 고정 보폭·시작선·파티클 진행량의 합이며 비중을 정확히 확정하지 않는다.
- 도착 랩까지 가속도 검출 걸음은 85·78·73·76이다. 특히 4층 왼쪽 정방향은 종료 전 3걸음이 추가돼, 이 숫자만으로 실제 보행의 걸음 수 차이를 판단하지 않는다.
- Android 하드웨어 step counter 차는 62·71·64·58로 가속도 검출보다 7~23걸음 적고, 콜백이 여러 걸음씩 늦게 들어온 구간도 있다.
- 저장된 `baseline_pdr`는 step counter 갱신과 방향 필터 영향을 함께 받아 종점 오차가 42.75·9.29·0·4.96m로 불안정하다. 이는 기존 엔진 전체의 공정한 성능값이 아니라 현재 비교용 MapMatcher 경로의 문제를 보여주는 진단값이다.

## 데이터 사용 판정

- **사용 가능**: 원시 IMU, 자기장, 기압, BLE, 랩 시각, `derived_fusion` 실제 예측의 재생·진단 자료.
- **오른쪽 자기장 지도 평가에 사용 가능**: 정·역방향 각 1회가 추가돼 leave-one-session-out 평가에 포함됐다.
- **아직 학습값 자동 반영 금지**: 자기장 적용 0회이고 새 두 회만으로 임계값을 낮추면 오보정 위험이 있다.
- **왼쪽 자기장 모델 확정 불가**: 이번에는 방향별 1회뿐이라 독립 검증용 반복이 부족하다.
- **BLE 운영 기준지문으로 직접 병합 금지**: 날짜 간 주소 ID 안정성이 낮다. payload/서비스 식별자의 다른 날 반복 검증 후 결정해야 한다.

## 3·6·8걸음 창의 별도 교차 검증

기존 iPhone 4층 오른쪽 복도 14회에서 한 회를 제외하고 다른 회차로 자기장 후보를 찾는 평가를 다시 실행했다. 이번 Galaxy 네 회의 성능값과 섞지 않는다. 3걸음은 270창 중 12창 채택, 채택 후보의 중앙 위치오차 2.44m였고 역방향 오인식이 있었다. 6걸음은 140창 중 13창 채택, 채택 후보 중앙오차 0.22m이나 역방향 채택 3창의 중앙오차가 3.40m였다. 8걸음은 100창 중 14창 채택, 채택 후보 중앙오차 0.15m, 14창 모두 2m 이내였다. 랩 사이 선형보간을 약한 정답으로 사용한 수치이며 같은 보행의 창끼리는 독립 표본이 아니다. 현재 Galaxy 로그에서는 8걸음 창 36개 중 적용 0회라, 이 iPhone 결과만으로 Galaxy의 6걸음 전환이나 문턱값 완화를 결정할 수 없다.

## 발견한 앱·분석 문제

1. 화장실 랩이 `오른쪽 끝 화장실 통로 앞 앞`, 역방향 코어 종점이 `코어복도 출구 중앙점 앞`으로 저장된다. 이미 위치 문구인 문자열에 `앞`을 다시 붙이는 라벨 정규화 문제다.
2. 기존 요약기는 `derived_fusion`을 세지 않아 예측 0개로 잘못 표시했다. `derived`, `derived_fusion`, `derived_fusion_final`을 모두 세도록 수정했다.
3. 자기장 지도 분석기는 예전 4층 단독 거리 50.193m와 현재 공용 거리 50.173m의 2cm 차이에도 중단됐다. 현재 navigation 거리표를 기준으로 삼고 5cm보다 큰 불일치만 오류로 처리하도록 수정했다.
4. 경로 수집 화면에서 모드4 좌표·구역만 보이고 가까운 강의실 후보가 빠져 있었다. 새 APK에서는 강의실 라인일 때 모드4 추정점에서 지도상 가까운 강의실 후보를 표시한다. 도면 기준 후보이므로 실제 강의실 앞 도착 판정과 구분한다.
   저장된 네 회의 마지막 모드4 위치에 같은 표시 계산을 대입하면 차례로 `4204`, `4213`, `4128`, `4120` 후보가 된다. 이는 화면 표시 로직 점검이며 해당 문 앞에 있었다는 실측 판정이 아니다.
5. AP 스캔이 0회인 이 네 보행으로 AP+자기장+BLE 결합 보정의 실효성을 평가할 수 없다. 자기장·BLE도 적용 0회이므로 현장 결과만으로 보정 가중치를 완화하지 않는다.

## 역방향 계단 출발점 정정 (2026-09-22)

Android 모드4 런타임은 역방향 경로를 시작할 때 계단 구역 사각형의 중심을 택했다. 기존 오른쪽 계단 시작 위치는 지도 x≈0.74, 사용자가 랩을 찍은 메인복도 쪽 실제 계단 입구선은 x=3.3631이다. 공용 거리표에서 약 1.86m 차이다. 왼쪽 계단의 중심과 입구선 차이는 약 0.33m였다. 지도 구역 자체는 변경하지 않고 역방향 시작 위치만 각 층 공용 거리표의 계단 입구선으로 교체했다.

동일 원시 로그의 근사 재생에서 오른쪽 역방향은 구역 중심 시작 시 종점 오차 3.78m, 입구선 시작 시 1.80m였다. 왼쪽 역방향은 1.51m→1.84m로 소폭 악화했다. 이 재생은 기존 휴대폰 현장 저장값(오른쪽 5.02m, 왼쪽 1.51m)을 완전히 재현하지 못하며 출발점 변경만의 방향성을 보는 실험이다. 실제 수정 APK의 보행 성능은 아직 측정하지 않았다. 나머지 오른쪽 약 3m, 왼쪽 정방향 약 4.9m의 누적 진행량 문제는 별도다.

## 왼쪽 초반 걸음·랩 시각 수정 및 진단 (2026-09-22)

기존 왼쪽 정방향 기록의 첫 걸음은 코어에서 진행량 약 -0.03m, 8번째는 `heading_unavailable`로 0m였다. 원시 회전 센서 이벤트는 8번째 걸음 무렵에도 들어왔지만 기존 로그에는 엔진에 보낸 heading 시각이 없어, 센서 미수신과 Android 콜백 시각·가속도 센서 시각의 순서 차이를 확정 분리할 수 없다. 엔진은 이제 heading 시각이 걸음보다 최대 250ms 앞서는 경우만 제한적으로 허용하며, Android는 콜백 현재 시각 대신 회전 센서의 실제 이벤트 시각을 보낸다. 250ms 초과 미래 방향이나 4초 초과 오래된 방향은 계속 거부한다.

경로 ID에서 초기 방향을 강제로 지정하는 별도 재생은 왼쪽 정방향 오차를 약 0.36m 줄였지만 오른쪽 정방향은 약 0.76m 악화시켜 운영 엔진에는 반영하지 않았다. 코어 첫 걸음의 거의 0m 진행은 원인이 확정되지 않아 임의 보상하지 않는다. 보폭·자기장·BLE 가중치도 그대로다.

새 Android 로그는 센서의 실제 이벤트 시각(`sensor_wall_time_ms`), WebView 예측 게시 시각, 랩 버튼 시각·예측 나이, 랩 직후 엔진 스냅샷과 마지막 입력·걸음 시각을 분리 저장한다. 다음 보행에서 랩 뒤 3걸음이 실제 이동인지 처리 대기인지 판단할 수 있다. 기존 네 회의 현장 저장 오차를 수정 APK의 성능으로 환산하지 않는다.
