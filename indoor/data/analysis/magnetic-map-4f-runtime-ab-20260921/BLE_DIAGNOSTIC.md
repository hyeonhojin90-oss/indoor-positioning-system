# 4층 최신 BLE가 모드 4 보정에 쓰이지 않은 원인

2026-09-21. 원시 로그, 현재 앱의 `ble-references.json`, Android `BleEnvironmentScanner`, 공용 `IndoorRuntime`/`IndoorZones`를 대조했다. 원본·앱 기준값은 바꾸지 않았다. 재생 결과는 `results.json`(현재 기준점)과 `diagnostic-same-day.json`(같은 날 기준점 진단)에 있다.

## 확인 결과

- 9월 19일 Galaxy 4층 오른쪽 복도 완주 `111300`(역방향)·`111532`(정방향)는 각각 BLE 403·314개를 수집했다. 종점 랩 전에는 391·300개다. 스캔 시작/종료도 정상 기록됐다.
- 앱이 사용 중인 4층 BLE 기준점 5개는 **9월 17일** 정지 측정으로 만들었다. 각 지문에 126~407개의 익명 ID가 있지만, 9월 19일 두 이동 로그 전체의 고유 ID 64·59개 중 현행 기준점 어느 곳과든 겹치는 것은 각각 12·9개다. 정방향 로그는 각 기준점과 겹치는 ID가 최대 4개뿐이다.
- 공용 분류기는 **같은 5초 창 안에서 동일 기준점 ID 5개 이상**을 요구한다. 이동 중 3초마다 평가한 창 14+11개 중 현재 기준으로는 관측이 부족한 창 4개, 공통 특징이 없는 창 21개였다. BLE가 파티클에 반영된 횟수는 **0/25**다.
- `111532` 전체 보행에서는 9월 17일의 4209 기준점과 겹치는 ID가 3개인 반면, **같은 날(9월 19일) 정지 수집한 4206 기준점과는 15개**가 겹친다. 같은 날 오른쪽 계단·코어 기준점과는 각각 18개가 겹친다. 9월 19일 정지 기준점을 진단용으로 메모리에서 만들어 쓰면 BLE는 두 보행에서 각각 3/14, 5/11창 적용됐다. 앱 기준점 파일을 덮어쓰지는 않았다.
- 현재 5개 공통 ID 조건을 3개로 낮춰도 9월 17일 기준점에서 통과할 가능성이 있는 창은 `111300`의 2개뿐이고 `111532`는 0개다. **임계값만 낮추는 것은 해결책이 아니다.**

|---|---|---:|---:|---:|---:|

| 정방향 `111532` | 앱의 9/17 기준 | 0/11창 | 4.003m | 7.685m | 3.998m |

9월 19일 정지 자료는 두 보행 **후에 수집된 별도 회차**이므로 사후 원인 진단용이다. 현장 당시 사용 가능했던 모델의 검증이나 다른 날 재현성 시험이 아니다. BLE 적용 가능성은 높아졌지만 정방향의 큰 진행량 오차는 거의 해결되지 않았고, 격자+BLE도 일관되게 좋아지지 않았다.

## 원인과 다음 검증

같은 Galaxy이고 스캔은 정상이다. 9월 17일 기준점이 9월 19일 이동 관측과 **ID 수준에서 잘 맞지 않는 것**이 직접 원인이다. Android 수집기는 `ScanResult.device.address`를 고정 문자열과 함께 SHA-256 해시한 앞 8바이트를 익명 ID로 쓴다. 실제 송신기가 주소를 바꾸면 같은 물리 송신기도 새 익명 ID가 된다. 날짜 간 겹침이 크게 줄어든 현상은 주소 변경과 양립하지만, 원시 주소를 저장하지 않아 주소 회전만이 유일한 원인이라고 확정할 수 없다. 송신기 가동 상태·수집 위치·스캔 환경 변화도 가능하다. 현재 로그에는 제조사 데이터 **존재 여부**만 있고 안정적인 광고 페이로드 식별자는 없다.

다음은 기준점 위치별로 안정적으로 반복되는 ID만 골라 **다른 날짜의 독립 보행**에서 공통 ID 수와 위치 성능을 확인하는 것이다. 주소 기반 ID가 계속 바뀐다면 고정 송신기의 서비스/제조사 페이로드에서 안정 필드가 실제 있는지 별도 조사해야 한다. 그 전에는 9월 19일 기준점으로 앱 기본 지문을 교체하거나 공통 ID 임계값을 낮추지 않는다.
