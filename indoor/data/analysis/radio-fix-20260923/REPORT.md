# BLE/AP 수정 및 RoNIN 추론 연결 — 2026-09-23

## 적용된 코드

1. BLE observeRadio의 앵커 파티클15% 생성을 제거했다. 연속 스캔/최소공통4개/약한 재가중은 유지한다. 후보1개 상대weight1은 새 좌표생성 권한이 아니다.
2. Wi-Fi 전용 절대점수를 분리해 공통AP4개 이상·기준지문공통비율10% 이상·RSSI RMS16dB 이하를 임시 채택조건으로 추가했다. 이 수치는 미수집 구역 오탐률로 보정된 임계값이 아니므로 최적조건이라고 주장하지 않는다. AP-only 관측이 기준을 못 넘으면 unknown/보류다.
3. AP1회는 새 파티클 생성/재표집을 하지 않고 기존 입자의 좌표를 유지한다. 앵커15m 밖 입자는AP항 중립, 안쪽은 최대1.2배의 양성 가중만 준 뒤 정규화한다. 미관측 구역에 0을 주지 않는다. 상대적인 질량은 달라질 수 있고 이후 PDR 재표집은 별도다. 강한 복구에도 절대채택조건이 필요하다.
4. 고정보폭 기본값 유지, Weinberg는 실험옵션 유지. AP 회전 이벤트 스케줄러는 이 작업의 점수 수정과 별개로 아직 미연결이다.

## AP 검사

정정된3개 기준점·2날짜·6회차로 질의회차 전체를 지문에서 제외하고15개 새 스캔을 따로 분류:15개 채택/15개 올바른구역/오판0. 이는 같은 기준점 내 상관된 스캔이며 독립15회 시험이 아니다. 운영 통합DB를 재학습한 것이 아닌 분류정책 진단이다. 실제 미수집 구역의 음성자료가 없어 unknown 오탐률은 미검증이다.

합성 검사로 공통ID없음/2개만겹침/RSSI20dB불일치 시 파티클 완전 유지, 알려진구역/미수집후보 혼재 시 모든좌표/미수집질량 유지, BLE 단일weight1 관측 시 새좌표가 생성되지 않음을 확인했다. 기존 AP 새스캔/중복제거/거리게이트 시험도 통과했다.

## RoNIN 실행 결과

공식 체크포인트의 실제CPU 추론을11개 원본보행에서 완료(성공11/실패0). 모델입력6축·출력속도2축,200샘플창, 좌표변환·시간보간·적분 연결. 우리데이터 학습/종점스케일보정 없음. 상세 입력/라이선스/해시는 `indoor/tools/ronin/README.md`와 `../ronin-android-20260923/evaluation.json`.

- 출발점 대비 변위 **크기** 평균오차:8.459m.
- 적분 경로길이 평균오차:6.641m.
- 위 수치는2D종점 위치오차가 아니다. 지도방위/파티클/BLE융합 미연결이며 첫1초미추정과 원본약45Hz자이로를200Hz로 보간하는 한계가 있다.
- 모든11회는 변위크기를 짧게 추정했다. 입력좌표/형상/유한출력 검증은 통과했으나 현재전처리의 성능이 나빠 앱기본엔진으로 승격하지 않는다. 속도학습/기기차이/회전원 등의 원인은 아직 분리되지 않았다.

## 실험 경우의 수

사용자 표현4×4×4=64는 명목상 맞지만 앱4모드가 자기장on/off와BLEon/off를 이미 포함하므로 자기장off모드에서 자기장방식4개는 같은 시험이다.

보폭4 × [자기장off의 BLE2조건 + 자기장on의 BLE2조건×자기장방식4] = **40개 고유조건**. AP on/off까지 독립축이면 이론80개이지만 AP없는보행로그로 실행됐다고 말할 수 없다. RoNIN은 별도속도프런트엔드이며40개 안에 아직 들어가지 않는다. 격자+V2 fallback 같은 추가혼합정책을 별도축으로 넣으면 다시 늘어난다. 목록/실행가능상태는 experiment-matrix.json.40개전체를실행한것은아니다.
