# GPS Module Instructions

루트 `AGENTS.md`와 함께 적용한다.

## 1. 목표와 범위

T-Beam을 이용해 버스 위치 정보를 안정적으로 수신하고 실제 오차를 측정·분석·보정한다. 최종적으로 동일 원시 데이터를 기준으로 보정 전후 결과를 비교할 수 있어야 한다.

- T-Beam GPS는 버스의 위치를 측정한다.
- 하차 후 사용자의 휴대폰 GPS는 향후 `app/` 영역에서 다룬다.
- 두 GPS 출처와 측위 주체를 코드·데이터·문서에서 혼합하지 않는다.

## 2. 작업 전 확인

1. `docs/GPS_STATUS.md`와 `docs/GPS_DECISIONS.md`를 읽는다.
2. 실제 장치 모델, GPS 칩, 펌웨어와 배선 정보를 확인한다.
3. 기존 `firmware/uno-raw-test`는 UNO·NEO-7M 시험 코드임을 확인한다.
4. Git 작업 트리와 기존 원시 데이터 존재 여부를 확인한다.
5. 데이터 수집인지 분석·보정 작업인지 범위를 구분한다.

확인하지 않은 T-Beam 핀, 보드 설정, 통신 속도와 제공 필드를 추측해 확정하지 않는다.

## 3. 기본 작업 순서

1. T-Beam 모델과 개발 환경 확인
2. GPS 원시 NMEA 수신
3. 사용 가능한 위치·품질 필드 확인
4. 원시 데이터와 메타데이터 저장
5. 정지·운행 상태 오차 분석
6. 보정 후보 비교와 방식 선정
7. 보정 코드 구현
8. 동일 원시 데이터로 테스트
9. 보정 전후 정확도·지연 비교
10. 실제 이동 환경 재검증과 결과 기록

데이터 분석 없이 특정 보정 방법을 최종 결정하지 않는다.

## 4. 원시 데이터 보호

- `data/raw`의 원본은 수정하거나 덮어쓰지 않는다.
- 보정·필터링 결과는 `data/processed`에 별도 저장한다.
- 원본 latitude·longitude와 보정 latitude·longitude를 구분한다.
- 원시 파일의 정리나 형식 변환이 필요하면 원본을 보존하고 새 파일을 만든다.
- 중요한 데이터 삭제·이동 전 정확한 대상을 확인하고 사용자 지시 없이 일괄 삭제하지 않는다.

## 5. 기록할 데이터

장치나 라이브러리가 실제 제공하는 경우 다음 필드를 함께 기록한다.

- `timestamp`
- `latitude`, `longitude`
- `altitude`
- `speed`
- `course` 또는 `heading`
- `satellite_count`
- `HDOP` 등 정확도·품질 정보
- GPS fix 상태와 fix 종류
- 원본 NMEA 문장

지원하지 않는 값을 추정해 원시 측정값처럼 만들지 않는다. 수집 장치, 펌웨어·코드 버전, 날짜, 장소, 샘플링 주기, 날씨와 주변 환경도 기록한다.

## 6. 완료 판정

다음은 진행상황이며 최종 완료가 아니다.

- GPS 파일이나 포트를 찾은 것
- T-Beam 연결 또는 프로그램 실행만 확인한 것
- 시리얼 문자열이나 위도·경도가 한 번 출력된 것
- 문제 원인과 수정 위치만 확인한 것
- 원시 데이터를 수집했지만 저장·검증하지 않은 것
- 필터 코드만 작성하고 정확도를 비교하지 않은 것

사용자가 GPS 수신 구현을 요청하면 지속 수신, 저장 형식과 가능한 실제 출력까지 검증한다. 보정을 요청하면 동일 원본을 이용한 보정 전후 평가까지 수행한다.

## 7. 기존 코드와 데이터 보호

- 정상 동작하는 원시 수신 기능을 불필요하게 변경하지 않는다.
- 새 보정 기능은 원시 수집 코드와 가능한 한 분리한다.
- 기존 UNO 시험 코드를 T-Beam 코드인 것처럼 수정하지 말고 새 하드웨어 구현은 별도 경로로 분리한다.
- 사용자 변경과 관련 없는 펌웨어·데이터를 되돌리지 않는다.

## 8. GPS 설계 결정 관리

다음과 같은 장기 결정은 `docs/GPS_DECISIONS.md`에 기록한다.

- 실제 T-Beam 모델과 GPS 칩
- 데이터 저장 형식과 필수 필드
- 선택한 보정 알고리즘과 선정 근거
- 샘플링 주기와 전송 방식
- 정확도 평가 기준

유명하거나 구현이 쉽다는 이유만으로 필터를 선택하지 않는다. 기존 결정과 다른 결과가 나오면 차이, 실험 근거와 영향 범위를 사용자에게 알린다.

## 9. 상태·결과 기록

- 의미 있는 단계가 완료되면 `docs/GPS_STATUS.md`를 갱신한다.
- 실험 조건과 결과는 `docs/GPS_RESULTS.md`에 누적한다.
- 전체 프로젝트 일정이나 문제가 바뀌면 루트 `docs/CURRENT_STATUS.md`도 갱신한다.
- 성공 사례뿐 아니라 오차, 지연, 수신 실패와 환경 조건을 기록한다.

## 10. 테스트 원칙

- 가능한 경우 실제 원시 데이터를 기준으로 평가한다.
- 정지와 이동 상태를 분리한다.
- 동일 경로를 반복 측정해 재현성을 확인한다.
- 평균 오차뿐 아니라 최대 오차, 표준편차, 좌표 튐과 지연을 확인한다.
- 코드 실행 성공과 위치 정확도 향상을 같은 결과로 판단하지 않는다.
